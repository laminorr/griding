# Both-Sides Cycle Audit — does the bot place & profit from ALL grid levels?

> **Bottom line:** In both-mode with **N** levels, the bot places **N** orders on
> init (**N/2 buy** below center / **N/2 sell** above center — given the wallet
> holds both BTC and IRT, or unconditionally in simulation), and a full round in
> which every placed level round-trips once produces **N** profit-making cycles
> (buy-initiated *and* sell-initiated cycles book profit identically). Therefore a
> "full round" box that sums over **`per_side`** (= N/2) cycles is **WRONG** — it
> should sum over **all N priced plan items (both sides)**, i.e. **N** cycles.
>
> **Important caveat (verified read-only):** the audited code (`main` @ `cac2803`,
> and this branch) does **not** currently render any "full round" green box. The
> grid calculator only shows a **per-single-cycle** net-profit line. So the fix is
> "specify the box correctly *before* building it": if/when a full-round total is
> shown, it must multiply/sum over **N**, never `per_side`.

This is a **read-only reconnaissance report**. No application code was modified.

## A. What does init actually place?

**Init path:** `TradingEngineService::initializeGrid()`
→ `GridCalculatorService::calculateGridLevels(mode)`
→ `TradingEngineService::placeGridOrders()`
→ `GridPlanner::plan(mode)`
→ `GridOrderSync::diff()`
→ `GridOrderExecutor::applyForBot(role: 'initial_grid')`.

### The planner produces BOTH sides in "both" mode

`GridPlanner::plan()` splits the level count evenly and generates buy levels below
`mid` **and** sell levels above `mid` in the same call:

- `app/Services/GridPlanner.php:84` — `$perSide = $mode === 'both' ? max(1, intdiv($levels, 2)) : max(1, $levels);`
- `app/Services/GridPlanner.php:90-103` — **buy** levels below mid: `if ($mode !== 'sell') { for ($i = 1; $i <= $perSide; $i++) { ... $factor = pow(1 - $step, $i); ... $rawItems[] = ['side' => 'buy', 'price' => $price]; } }`
- `app/Services/GridPlanner.php:106-113` — **sell** levels above mid: `if ($mode !== 'buy') { for ($i = 1; $i <= $perSide; $i++) { ... $factor = pow(1 + $step, $i); ... $rawItems[] = ['side' => 'sell', 'price' => $price]; } }`

So for **N=4, both**: `per_side = 2` → **2 buy items + 2 sell items = 4 plan items**.

### Both sides are executed at init (not just buys)

`placeGridOrders()` calls the planner with the bot's real mode and hands the entire
diff (both sides) to the executor:

- `app/Services/TradingEngineService.php:662-671` — `$plan = $this->gridPlanner->plan($symbol, ..., mode: $mode, ..., presetBaseQty: $presetBaseQty);`
- `app/Services/TradingEngineService.php:674` — `$diff = $this->gridOrderSync->diff($plan, []);` (initial setup = "diff against empty existing orders", so every planned level becomes a `to_place` item).
- `app/Services/TradingEngineService.php:734` — `$this->gridOrderExecutor->applyForBot($botConfig->id, $diff, simulation: $simulation, role: 'initial_grid');`

`GridOrderExecutor::applyForBot()` creates one `grid_orders` row per `to_place`
item, stamping the plan's `side` into the `type` column and `role='initial_grid'`:

- `app/Services/GridOrderExecutor.php:174,178` (simulation) and `:214,217` (live) — `'type' => $side, ... 'role' => $role`.

`grid_orders.type` is the enum `['buy','sell']`
(`database/migrations/2025_07_24_215103_create_grid_orders_table.php:20`); there is
no separate `side` column — **`type` IS the side**. `role` is
`['initial_grid','cycle_exit','rebalance','manual']`
(`database/migrations/2026_06_27_000002_add_role_to_grid_orders.php:24`).

### Are the upper sells REAL initial orders, or only reactions to a buy?

**They are real initial orders placed at start** — the sells above center are
generated by the planner and executed in the same init pass as the buys, *not*
created later as continuations. The continuation mechanism (Part B) is a *separate*
path (`CheckTradesJob::createPairOrder`) that only runs when an order fills.

Placing a sell requires holding base currency (BTC). How init handles that differs
by mode:

- **Simulation bots (bot 46 is one):** the SELL-side balance pre-filter is
  **skipped entirely**, so *all* sells are placed regardless of any balance:
  - `app/Services/TradingEngineService.php:611` — `$needsBalanceCheck = $plannedSell > 0 && $mode !== 'buy';`
  - `app/Services/TradingEngineService.php:613` — `if ($needsBalanceCheck && !$botConfig->simulation) { ... }` (balance fetch skipped for sim)
  - `app/Services/TradingEngineService.php:679` — `if ($needsBalanceCheck && !$botConfig->simulation) { ... }` (pre-filter skipped for sim)
  - `computePresetBaseQty()` also returns `null` for sim (`app/Services/TradingEngineService.php:809-811`), so sells use the ordinary `fixedQty` sizing.
- **Live bots:** init **does** place the sells, but only those the account can
  currently back with real BTC. It fetches the base balance
  (`app/Services/TradingEngineService.php:613-624`) and, per sell item, deducts the
  required BTC and drops any sell it cannot cover
  (`app/Services/TradingEngineService.php:679-716`, the `continue; // Skip this SELL order` at `:699`). Buy-side IRT sufficiency is checked separately in
  `verifySufficientQuoteBalance()` (`app/Services/TradingEngineService.php:400-464`).

**Conclusion for the user's scenario** (wallet holds both BTC and IRT): init places
**all N levels** — N/2 buys (backed by IRT) and N/2 sells (backed by existing BTC).
The upper sells are genuine initial orders, not deferred reactions.

## B. How does a cycle complete on EACH side?

The continuation + booking engine is fully **symmetric** — it does not care which
side filled first.

### Continuation order (opposite side) — `createPairOrderLocked()`

- `app/Jobs/CheckTradesJob.php:709` — `$newType = $filledOrder->type === 'buy' ? 'sell' : 'buy';` (a filled buy → sell continuation; a filled sell → buy continuation).
- `app/Jobs/CheckTradesJob.php:714-717` — continuation price: sell = `price × (1 + spacing)` (above), buy = `price × (1 - spacing)` (below):
  `$rawPrice = $newType === 'sell' ? Money::mul($filledOrder->price, Money::add('1', $spacingStr)) : Money::mul($filledOrder->price, Money::sub('1', $spacingStr));`
- `app/Jobs/CheckTradesJob.php:793-802` — the continuation row is created with `'role' => 'cycle_exit'` and back-linked via `paired_order_id`.

So **yes**: an initial SELL that fills first spawns a BUY continuation below it,
exactly mirroring a filled BUY spawning a SELL continuation above it.

### Booking a completed cycle — `createCompletedTradeIfPaired()`

- `app/Jobs/CheckTradesJob.php:620-623` — books only when **both** legs are `filled`.
- `app/Jobs/CheckTradesJob.php:632-634` — assigns buy/sell roles **regardless of fill order**:
  `[$buyOrder, $sellOrder] = $order->type === 'buy' ? [$order, $partner] : [$partner, $order];`
- `app/Jobs/CheckTradesJob.php:652` → `recordCompletedTrade()` → `app/Jobs/CheckTradesJob.php:976` — `CompletedTrade::createFromOrders($buyOrder, $sellOrder)`.

`CompletedTrade::createFromOrders()` is direction-agnostic: it computes
`gross = (sellPrice − buyPrice) × amount` and nets two-leg fees:

- `app/Models/CompletedTrade.php:380` — `$grossProfit = Money::mul(Money::sub($sellPrice, $buyPrice), $amount);`
- `app/Models/CompletedTrade.php:397-402` — two-leg fee and `netProfit`.

For a **sell-first** cycle the initial sell price is *higher* and the continuation
buy price is *lower*, so `sellPrice − buyPrice > 0` → positive profit, booked by the
**same** `CompletedTrade::createFromOrders()` as a buy-first cycle. **Confirmed:
sell-initiated cycles record profit identically to buy-initiated cycles.**

> Note on denomination: the task frames buy-levels as "earning IRT" and sell-levels
> as "earning BTC". The code books **both** as an IRT-denominated net profit
> `(sellPrice − buyPrice) × amount − fees` (`CompletedTrade.php:380,402`). This is
> economically equivalent — a sell-first round-trip returns the same BTC quantity
> plus a net IRT gain — but if the UI ever wants to present sell-side gains in BTC
> terms, that is a *presentation* choice; the booked ledger value is IRT for every
> cycle.

## C. So how many profit-producing cycles are in a "full round"?

**A full round = N cycles (all placed levels), NOT `per_side`.**

- Init places **N** orders: `per_side` buys + `per_side` sells (Part A).
- Every one of those N initial orders can round-trip **once**: each initial buy
  → sell-continuation → 1 booked cycle; each initial sell → buy-continuation →
  1 booked cycle (Part B, fully symmetric).
- Therefore, when every placed level completes once, the number of booked
  `completed_trades` = **N = 2 × per_side**.

The per-cycle economics are the same on both sides, so the total is well-defined.
For any level of notional `M` at spacing `s`, gross per round-trip is `M × s`
whether it started as a buy or a sell:
- buy P → sell P(1+s): `gross = (P(1+s) − P) × qty = P·s·qty = M·s`
- sell P → buy P(1−s): `gross = (P − P(1−s)) × qty = P·s·qty = M·s`

This matches `GridCalculator`'s per-cycle formula
`grossPerCycle = repNotional × (spacing/100)`
(`app/Filament/Pages/GridCalculator.php:204`) — and it holds for **both**
directions.

**Explicit answer for N=4 both-mode:** the honest "full round" is **4 cycles**
(2 buy-initiated + 2 sell-initiated), **not 2** (`per_side`).

### D3. Do BOTH sides actually produce profit? (buy-first vs sell-first cycles)

A cycle's **initiating** leg is the one with `role='initial_grid'`; the
**continuation** leg is `role='cycle_exit'`. Buy-first ⇒ the buy leg initiated;
sell-first ⇒ the sell leg initiated.

```sql
SELECT
  CASE
    WHEN b.role = 'initial_grid' AND s.role = 'cycle_exit'  THEN 'buy_first'
    WHEN s.role = 'initial_grid' AND b.role = 'cycle_exit'  THEN 'sell_first'
    ELSE 'other/ambiguous'
  END AS cycle_origin,
  COUNT(*)            AS cycles,
  SUM(ct.net_profit)  AS total_net_profit,
  MIN(ct.created_at)  AS first_seen,
  MAX(ct.created_at)  AS last_seen
FROM completed_trades ct
JOIN grid_orders b ON b.id = ct.buy_order_id
JOIN grid_orders s ON s.id = ct.sell_order_id
WHERE ct.bot_config_id = 46
GROUP BY cycle_origin;
```

A cross-check that does not depend on `role` (uses which leg was created first):

```sql
SELECT
  CASE WHEN b.created_at <= s.created_at THEN 'buy_first' ELSE 'sell_first' END AS cycle_origin,
  COUNT(*)           AS cycles,
  SUM(ct.net_profit) AS total_net_profit
FROM completed_trades ct
JOIN grid_orders b ON b.id = ct.buy_order_id
JOIN grid_orders s ON s.id = ct.sell_order_id
WHERE ct.bot_config_id = 46
GROUP BY cycle_origin;
```

Sample of individual cycles with both legs' roles/types:

```sql
SELECT ct.id, ct.buy_order_id, ct.sell_order_id,
       b.type AS buy_leg_type,  b.role AS buy_leg_role,
       s.type AS sell_leg_type, s.role AS sell_leg_role,
       ct.buy_price, ct.sell_price, ct.net_profit, ct.created_at
FROM completed_trades ct
JOIN grid_orders b ON b.id = ct.buy_order_id
JOIN grid_orders s ON s.id = ct.sell_order_id
WHERE ct.bot_config_id = 46
ORDER BY ct.created_at ASC
LIMIT 40;
```

**Interpretation guide:**
- If D1 shows `initial_grid` rows split ~evenly into `buy` and `sell` → init places
  both sides (confirms A empirically).
- If D3 shows a **non-zero `sell_first` row with positive `total_net_profit`** →
  the sell side really does round-trip and book profit (confirms B empirically, and
  proves a full round is N, not per_side).
- If D3 shows `sell_first = 0`, that would mean the sim's price path simply never
  drove an initial sell to fill before its pair (a market-path artifact, not a code
  limitation) — the code path in B still books sell-first cycles when they occur.

## E. If the "full round" box is wrong — exact spec for the fix (do NOT implement)

**Current state:** there is **no** "full round" box in the audited code. The
calculator renders only per-single-cycle numbers:
- `app/Filament/Pages/GridCalculator.php:203-207` compute `grossPerCycle`,
  `feePerCycle`, `netPerCycle` for **one** cycle from a single representative
  notional (`repNotional`, the first priced item — `:192-199`).
- `resources/views/filament/pages/grid-calculator.blade.php:607-649` renders that
  "کارمزد و سود هر چرخه" (fee & profit *per cycle*) panel. The note at
  `:639` explicitly says *"یک چرخه = یک خرید و یک فروش کامل روی یک پله"* (one cycle
  = one full buy+sell on one level). `per_side` appears only as an informational
  label (`blade:380`, `blade:539`), never as a profit multiplier.

**Therefore:** if a "full round" total box is added (or exists in an unmerged
variant) and it multiplies/sums by `per_side`, it is **WRONG**. The correct
"full round" is **every placed level completing one cycle = N cycles**.

**Exact specification for a correct full-round box:**

1. Sum over **all priced plan items, both sides** — i.e. every element of
   `$plan['items']` with `notional > 0` (this is `count($items)` = **N** in the
   normal case, not `per_side`).
2. Per-item net = `item.notional × (spacing/100)  −  2 × item.notional × (feeBps/10000)`
   (the same formula already at `GridCalculator.php:204,206`, but applied
   **per item** rather than to a single `repNotional`). Then
   `fullRoundNet = Σ over priced items`.
   - Equivalent simple form when budget-mode makes notionals uniform:
     `fullRoundNet ≈ netPerCycle × (number of priced items)` — again the multiplier
     is **N**, never `per_side`.
3. The engine formula is confirmed **identical for sell-initiated cycles**
   (Part B / Part C: `gross = notional × spacing` holds for both directions, and
   `CompletedTrade::createFromOrders` books both the same way), so summing every
   placed level's cycle-net is exactly correct — no per-side asymmetry to worry
   about.
4. Label it honestly, e.g. *"سود یک دور کامل (همه سطوح یک‌بار)"* = "profit of one
   full round (every level once)", and keep it clearly separate from any
   time-based projection (the page deliberately avoids day/week/month
   extrapolation — see `GridCalculator.php:31-36`).

**One-line summary of the fix:** change the multiplier/sum basis from `per_side`
(N/2) to **all N priced plan items (both sides)**; no engine change is needed
because sell-initiated cycles already book profit identically.
